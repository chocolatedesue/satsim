# 协同仿真实验：轨道时变拓扑下的在轨推理调度

引擎架构见 `docs/adr/0005-cosim-contact-trace.md`，复现与回放说明在文末。

## 核心问题

前期 orbitsim 纯几何分析（`research_out/README.md`）提出两个假设：
1. **地影可预知**：卫星进出地影的时刻完全由轨道决定，靠星历在首次放置时就能避开暗星；
2. **接触窗口短**：遥感星（RS）到算力星的单条激光链路接触只有分钟级，这可能是迫使请求在运行中迁移的主要原因。

但纯几何分析没有真正跑过请求流。本实验把 orbitsim 导出的接触与地影轨迹接入 satsim 的流体网络与推理耗时模型，回答一个直接问题：**在真实的轨道时变拓扑上，运行中迁移到底比"只靠星历做首次放置"多赚多少达标率？**

> 注：本协同仿真先通过**多轨道面异构 SSO（`multi_sso`）**验证传统无感知任务分配（`nearest` / `rr` / `random` / `least_loaded`）确实存在严重的**计算负载明暗错配与暗星队列积压（Motivation）**；再在真实时变拓扑上对比四档轨道/算力感知策略（`greedy` / `reactive` / `ephemeris` / `contact_aware`）。自研迁移 `rebalance_ours`（CCE-Net，占带宽迁移）在 `satsim.method` 的静态环/双轨拓扑主实验（`exp_ring_s1_cost_claims_v3` 等）中已实现并运行，结论见仓库 README 主表。

## 前置问题确认（Motivation）：多轨道面异构 SSO 下的计算负载错配（`exp_motivation_multi_sso`）

在进入复杂调度与跨星迁移之前，首先需要用最常见的传统任务分配算法（不开启运行中迁移，`migrate: none`）回答一个基本问题：**在多轨道面异构星座上，如果直接用就近卸载（`nearest`）、轮询（`rr`）、随机（`random`）或最短队列（`least_loaded` / JSQ），计算负载到底会出什么问题？**

### 合成星座与实验设置（`satsim.cosim.synth.synth_multi_sso`）
- **遥感星（RS）**：3 颗光学遥感星（`RS-1030a`、`RS-1030b`、`RS-1330`，500 km），单激光终端就近接入算力星（视距 ≤ 4000 km）。
- **多轨道面异构 SSO 算力星座（3 × 10 = 30 颗算力星，550 km）**：面内 10 星相隔 $36^\circ$ 组成全时常连环路，跨面采用 `+Grid`（≤ 5000 km 在线）：
  - **2 个成像伴随影轨（`LTAN 10:30`、`LTAN 13:30`，共 20 颗星）**：离光学遥感星最近，但每圈有 **~36% 时间进入地影**（限功 80 W，时钟降频至 $f_{\text{dark}} = 0.35\times$）；
  - **1 个晨昏全亮轨（`LTAN 06:00`，10 颗星）**：**0% 时间进影（100% 满频 $f = 1.0\times$）**。
- **负载**：每颗 RS 每分钟提交 10 个请求（50% 为 1.6万–3.2万 token 的长任务，截止时间 = $2\times$ 亮星独占解码耗时），3 种子均值。

### 三条核心机制发现
1. **`nearest`（就近分配）导致“空间可达性与光照算力的严重错配”**：光学遥感星位于 `LTAN 10:30 / 13:30`，就近最短跳数卸载把 **87.3%** 的任务压在同面影轨上，全亮满血的晨昏轨（`LTAN 06:00`，占 1/3 算力星）仅分到 **12.7%**；暗星队列积压至亮星的 **1.39×**，解码耗时膨胀 **2.70×**。
2. **`rr`（轮询）与 `random`（随机）掉入“Little's Law 暗星队列雪球陷阱”**：即便按卫星数量均匀派发请求（20.1% 直投当前暗星），由于暗星解码速度仅为亮星的 $0.35\times$（单步耗时 $2.86\times$），请求在暗星滞留时间远长于亮星，导致暗星实时并发队列（5.57）反超亮星（4.43）达 **1.26×**，进一步拉大批次耗时。即便使用感知队列长度的 `least_loaded`（JSQ），因不区分明暗算力，仍有 16.0% Token 在影内慢速解码，长任务达标率仅 85.6%。
3. **从“算力/星历感知分配”到“高负载下运行中迁移”的清晰递进**：在中轻载下，感知算力与星历的初次分配（`greedy` / `ephemeris`）把暗/亮星队列比从 `1.26×` 反转为 `0.25×`，长任务达标率提升至 97.4%–99.7%；而在重载（`rate=12`）下，亮星队列趋于饱和，仅靠初次放置（`ephemeris` 83.7%）已不够，必须结合外部性感知的运行中迁移（`contact_aware` **90.3%**）才能进一步削峰填谷。

## 五条结论

1. **有星间网格时，接入切换被多跳中继吸收了。**
   Walker 场景里 RS 每小时换 12 次接入星，但只要连上任意一颗算力星，就能经面内环和跨面链路转发到全网 40 颗星。结果回传几乎不用等（deliver gap 接近 0），迁移中止 0 次。因此"单链路接触 7–8 min 就会迫使迁移"在带 ISL 网格的星座里不成立，论文表述需要修正。

2. **性能差距主要来自地影，而且约 85% 靠首次放置就能拿到。**
   从 `greedy` 到 `ephemeris`，长任务达标率从 95.9% 升至 99.3%（+3.4 个百分点）；加上运行中迁移（`contact_aware`）再升至 99.9%（+0.6 个百分点）。总计 4.0 个点的提升中，约 85% 来自星历放置，运行中迁移贡献约 15%，验证了几何分析的判断。

3. **"进影才搬"的反应式迁移不如不迁移的星历放置。**
   `reactive` 把影内解码压到了 0.2%，但长任务达标率只有 97.1%，低于 `ephemeris` 的 99.3%。原因是它先把请求放到快进影的卫星上，进影后再花时间搬走，且目标星选择不看未来星历。这张表直接回答了"为什么不能等进地影再搬"。

4. **簇间不连通时，交付卡在下一次过境，调度救不了。**
   S-SSO2 的 4 个算力簇彼此从不进入 5000 km，RS 每小时只能碰到一次算力簇。长任务交付 p90 高达 33 min，约 30% 请求超时；四种策略差距不到 2 个百分点。因为同簇 4 星几乎同时进地影（首尾时差 ≤ 100 s），簇内没有亮星可迁。这类构型的瓶颈在拓扑设计，不在调度算法。

5. **10 Gbps 星间链路下，带宽不是瓶颈。**
   1.6 GB 的 KV 状态在 10 Gbps 链路上只需 1–2 s，远短于分钟级的接触窗口和地影时长。要让带宽争用（C2）成为显著瓶颈，需要把链路带宽压到 0.1–0.5 Gbps 量级，或叠加遥感数传背景流。

| 截止 2×，45 请求/分钟 | 96.1% | 99.4% | 99.9% |

当截止时间收紧到 1.5× 时，排队等待成为主导因素。当前 `ephemeris` 只优化新请求自身的预计交付时间，没算它插入队列后把同节点已有请求拖慢的外部性，结果反而输给 `greedy`。这是下一版调度器要补齐的代价项。

## 场景三：台风应急下的长时 agentic 会话（`cosim_typhoon_agentic_v1`）

**故事**：春分日两小时，RS-1030 / RS-1330 / RS-SAR 持续成像台风区，每颗每分钟提交 12 个请求。一半是长时 agentic 会话（变化检测、灾情报告，2–4 万 token，在亮星上独占解码也要 4–9 分钟，实际排队后 10–30 分钟），一半是短问答。这类会话长度和地影（每圈约 35 分钟）是同一量级，是迁移最可能有用的情形。轨迹同 Walker 53° 4×10；长会话截止 = 到达 + 2× 亮星独占解码时间。

跑的过程中发现第一版接触感知迁移有个真问题：它给迁移打分时只算迁移者自己的交付时间，不算搬进去后把目标星上已有请求拖慢多少；同一个控制周期里又会有很多请求同时看上同一颗亮星。负载一高，亮星被挤爆，反而输给不迁移。**v2** 改成按"一对节点"算净收益：

> 净收益 = 迁移者预计交付提前量 + 源星上剩余请求因此变快的量 − 目标星上已有请求因此变慢的量
> （每一项 = Δ 单步时间 × 剩余 token）；每个控制周期每颗目标星最多接 1 个迁入，有在途迁入的星先跳过。

v1 保留为 `contact_aware_v1` 作对照。前两个场景的表里 `contact_aware` 是 v1 的数；在 Walker 45 请求/分钟下 v2 是 100% / 迁移 599 次，v1 是 99.9% / 304 次；S-SSO2 下 v2 是 71.5% / 迁移 79 次，v1 是 69.4% / 90 次。结论不变。仓库里的回放数据已用 v2 重新生成。

**主实验**（12 请求/分钟/星，约 3.4k 请求，3 种子均值）

| 策略 | 长会话达标 | 全部达标 | 长会话 p90 | 迁移次数 |
|---|---|---|---|---|
| `greedy` | 60.4% | 80.3% | 29.3 min | 0 |
| `reactive` | 41.5% | 71.0% | 20.5 min | 1259 |
| `ephemeris` | 60.5% | 80.5% | 28.4 min | 0 |
| `contact_aware_v1` | 53.3% | 77.0% | 20.7 min | 1634 |
| `contact_aware` (v2) | **64.3%** | **82.4%** | 27.3 min | 718 |

**负载扫描**（长会话达标率，2 种子均值）

| 请求/分钟/星 | greedy | reactive | ephemeris | v1 | v2 |
|---|---|---|---|---|---|
| 4 | 98.9% | 100% | 99.9% | 100% | 100% |
| 8 | 93.2% | 95.3% | 98.5% | 92.3% | **99.9%** |
| 12 | 62.7% | 44.9% | 62.4% | 58.4% | **66.4%** |
| 16 | 44.5% | 26.6% | 45.6% | 31.5% | **47.7%** |

**读法**

1. **轻载时谁都行，重载时反应式迁移是负优化。** 12/分钟时 reactive 把达标率从 60% 拖到 42%。回放里能看到原因：一颗星进影，它上面的请求同一秒全部涌向同一颗亮星（1:08:20 一秒内 6 条迁移从 C/p0s6 飞向 C/p0s3），亮星立刻过载。
2. **只算自己的迁移也一样。** v1 迁移 1634 次，达标率 53%，低于不迁移。迁移本身不贵（KV 在 10 Gbps 上 1–4 秒传完，中止 0 次），贵的是搬进去之后对目标星的拖慢。
3. **把外部性算进去后，迁移才稳定地有正收益。** v2 在 8/12/16 三个负载下都是最高，比星历放置高 1.4–4 个点，迁移次数反而比 v1 少一半。这是目前唯一证明"运行中迁移"在星历放置之外还有实际收益的证据。
4. **重载下星历放置和贪心一样。** 12/16 时两者差不到 1 个点：队列压力压过了地影，放置时只看单请求交付时间不够。

**对论文的含义**：迁移机制的卖点不应是"躲地影"本身（放置就能做大半），而是"过载时怎么迁才不会把系统拖垮"。反应式和只算自己的迁移都是很自然的基线，而且在重载下都输给不迁移，这是个清楚的对照。

## 对论文叙事的启示

- **不要把迁移动机写成"接触窗口短"**：有 ISL 网格时接入切换被中继吸收，没有网格时迁移也无处可去。
- **立得住的三条主线**：
  1. `ephemeris`（星历放置）是必须列入对比表的强基线；
  2. 运行中迁移在常规条件下带来 0.5–1 个百分点的增量，需要靠更紧的截止时间、更长的多轮会话或不可预知的功率波动来放大；
  3. 拓扑连通性对交付时延的影响远大于调度策略（S-SSO2 p90 33 min vs Walker 5.5 min）。

## 当前局限

- 地影简化为固定限功（80 W / 0.35×），未建电池充放电与热模型；
- 未计入 prefill 算力开销与激光链路重捕获时间；

## 怎么看回放

协同仿真结果可以在 orbitsim 的 3-D 回放页 `http://localhost:5288/play.html` 中直接观看（见 `../orbitsim/viz/README.md`）：

- **切场景与策略**：左上角下拉框切换 `cosim_coop_w53_v1`（网格连通）与 `cosim_coop_sso2_v1`（簇间断联）；按数字键 `1`–`4` 或直接点击策略对比表的行切换四种策略。
- **看迁移与断链**：地球上默认只画橙色 KV 迁移箭头（带移动圆点）和红色断链/中止标记；需要看高频的请求上传/结果回传时，勾选"显示上传/回传"。
- **快速定位**：点"跳到下一次迁移"按钮直接跳到下一条 KV 迁移发生时刻；用 `Space` 暂停/播放，`←` / `→` 前后跳 60 秒。

## 复现命令

```bash
# 0. 前置问题确认（Motivation）：即时合成多轨道面异构 SSO 并运行任务分配与计算负载诊断
uv run python scripts/exp_motivation_multi_sso.py --seeds 1,2,3 --rate 10 --sweep-rates 6,8,10,12

# 1. orbitsim：重新生成固定接触轨迹（可选，input/traces/ 已含导出文件）
cd ../orbitsim && uv run python export_cosim.py && cp cosim_out/*.json ../satsim/input/traces/

# 2. satsim：运行协同仿真并导出前端回放 JSON
uv run satsim-cosim configs/cosim_coop_w53_v1.yaml --viz ../orbitsim/viz/public/playback
uv run satsim-cosim configs/cosim_coop_sso2_v1.yaml --viz ../orbitsim/viz/public/playback
uv run satsim-cosim configs/cosim_typhoon_agentic_v1.yaml --viz ../orbitsim/viz/public/playback
uv run python scripts/cosim_sweep.py configs/cosim_typhoon_agentic_v1.yaml workload.rate_per_rs_per_min 4 8 12 16 --seeds 1,2

# 3. 灵敏度扫描
uv run python scripts/cosim_sweep.py configs/cosim_coop_w53_v1.yaml slo.deadline_factor_long 1.5 2 3 --seeds 1

# 4. 启动 3-D 回放页面
cd ../orbitsim/viz && npm run dev   # 打开 http://localhost:5288/play.html
```
